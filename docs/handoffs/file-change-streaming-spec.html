Live, authoritative file-change streaming

An execution contract for making edits appear immediately and finish with complete diffs in Zyra desktop and TUI, without copying obsolete provider behavior.

01 — agent mission

The goal the implementation agent owns

Goal
Make every file mutation visible at start, progressively accurate while running, and authoritative at completion—using one stable activity identity per operation.

This must work for Zyra’s desktop assistant runtime and root TUI, across Pi and Codex provider event shapes, while preserving existing sessions and rendering behavior.

First action for the implementation agent: read this spec and the companion research plan, inspect the named current files, then implement Work Package 00 fixtures before changing runtime behavior.

Companion research: docs/plans/file-change-streaming.html contains the source findings, protocol baselines, evidence index, and architectural rationale. This spec is the execution contract when the two documents differ in purpose.

02 — mandatory requirements

What the completed feature must do

  • Immediate row: create a running file-change activity/component from the provider start event, without waiting for completion or final narration.
  • Stable identity: all preview, live, completion, and reconciliation events for one operation update the same activity ID.
  • Progressive data: add known paths and provisional patch data as soon as usable arguments or structured live changes exist.
  • Authoritative completion: promote Pi result details and current Codex structured changes into canonical file-change data.
  • Monotonic merge: delayed or provisional events cannot regress completed status or overwrite higher-authority patch data.
  • Desktop access: mounted per-file Diff actions open the existing diff panel on the correct file, including a live preview.
  • TUI reconciliation: provisional call preview becomes authoritative result output inside the same mutable tool component.
  • Write honesty: write-existing uses an execution-boundary snapshot or remains explicitly preview-only; no false before/after diff.
  • Backward compatibility: old persisted activities containing only legacy patch/paths fields continue to render.
  • Bounded data: large/binary files and patch payloads have safe caps and explicit unavailable/truncated states.
03 — scope boundary

Change only what the lifecycle requires

In scope

  • Provider-neutral file-change payload contract and merge helpers.
  • Pi desktop result-details extraction and preview/result authority.
  • Current Codex item/fileChange/patchUpdated support.
  • Final turn-diff reconciliation with safe matching.
  • Minimal mounted desktop diff-panel state and callbacks.
  • TUI file-change-specific state and authoritative rendering.
  • Write preview and safe authoritative write-existing strategy.
  • Focused fixture, rendering, lifecycle, and targeted type checks.

Out of scope

  • Replacing AssistantDiffPanel or PatchDiffViewer.
  • Making desktop and TUI visually identical.
  • Copying unrelated DevScope playground/settings/plan-panel code.
  • Changing DevScope or Codex source repositories.
  • Removing legacy persisted activity support.
  • Broad assistant timeline or sidebar redesign.
  • Routine production builds, Rust builds, deploys, or packaging.
  • Unrelated cleanup or refactors discovered during implementation.
Repository safety: preserve all unrelated local changes. The desktop app under apps/zyra-ui/ is ignored by the root Git configuration, so absence from a root diff does not prove desktop files were unchanged.
04 — normalized interface

The data contract the agent must implement

type FileChangeSource =
  | 'args-preview'
  | 'provider-live'
  | 'provider-result'
  | 'turn-final'
  | 'synthetic-snapshot'

type NormalizedFileChange = {
  path: string
  previousPath?: string
  kind: 'add' | 'delete' | 'update' | 'move'
  diff?: string
  isNew?: boolean
}

type NormalizedFileChangePayload = {
  category: 'file-change'
  provider: 'codex' | 'pi'
  status: 'running' | 'completed' | 'failed'
  toolName?: string
  itemId?: string
  toolCallId?: string
  revision: number
  source: FileChangeSource
  authoritative: boolean
  changes: NormalizedFileChange[]
  paths: string[]
  createdPaths: string[]
  patch?: string
  previewPatch?: string
  additions?: number
  deletions?: number
  startedAt: string
  completedAt?: string
  durationMs?: number
  output?: string
}

Required invariants

Stable identity

Codex keeps codex-item-${itemId}; Pi keeps zyra-tool-${toolCallId}.

Monotonic status

Completed/failed cannot regress to running after delayed delivery.

Monotonic authority

Preview data cannot replace provider-result or accepted final data.

Preserved metadata

Identity, start time, paths, output, and error remain through enrichment.

Idempotent replay

Replaying an accepted revision cannot append or duplicate data.

Safe ambiguity

An uncertain turn diff stays separate instead of attaching to a guessed activity.

Authority order

SourceRankRequired behavior
args-preview1Immediate provisional display only.
provider-live2Replace same-file live snapshots; never concatenate complete snapshots.
synthetic-snapshot3Authoritative only for an exactly correlated successful write call.
provider-result4Canonical completion for represented files.
turn-final4 / reconciliationFill missing/incomplete final files while preserving the real item activity.

06 — ordered work packages

Implementation sequence and proof gates

00

Provider fixtures and pure contract tests

Implement

  • Fixtures for Pi edit start/update/end with result details.
  • Fixtures for Pi write-new/write-existing/failure.
  • Fixtures for Codex started/patchUpdated/completed/final turn diff.
  • Cases for multi-file, move, delete, duplicate revision, and out-of-order delivery.
Gate: fixture expectations encode identity, authority, status, and no-duplicate behavior before adapter edits begin.
01

Shared desktop contract and merge policy

  • Add normalized types/guards under shared assistant contracts or a focused sibling.
  • Add named file-change merge helpers.
  • Retain fallback reads for legacy patch/paths.
  • Recompute paths, created paths, file count, additions, and deletions from accepted canonical data.
Gate: pure tests prove monotonic status/authority, replay safety, metadata preservation, and safe turn reconciliation.
02

Pi desktop adapter

  • Extract result and partial-result details before argument fallback.
  • Emit preview and completion on the existing zyra-tool-* ID.
  • Keep raw result only for compatibility/debugging; render from bounded normalized fields.
Gate: Pi lifecycle test shows immediate path/preview and authoritative result patch on one activity.
03

Current Codex live updates

  • Add explicit item/fileChange/patchUpdated handling before generic deltas.
  • Normalize add/delete/update/move, including movePath.
  • Keep old output-delta fixture as fallback coverage only.
Gate: started → multiple patch snapshots → completed remains one activity with latest accepted change data.
04

Mounted desktop diff flow

  • Add selected diff target and minimal panel state to AssistantPage.
  • Replace onViewDiff={undefined} with a real callback.
  • Mount the existing AssistantDiffPanel.
  • Keep live selection keyed by activity ID + path.
Gate: click-through opens the correct running/completed file and live revision refresh does not remount the panel.
05

TUI file-change state and rendering

  • Normalize preview/result details before generic tool rendering.
  • Use Pi result diff for terminal context and patch for stats/fixtures.
  • Bound context; preserve width and expansion.
  • Update one mutable component; retain failed preview as explicitly uncommitted.
Gate: rendering regressions prove immediate preview, authoritative replacement, one card, failure labeling, and width safety.
06

Write-existing authoritative diff

  • Prefer a wrapped/enriched write tool with bounded pre-write snapshot inside execution.
  • Clean snapshot state on every exit path.
  • For oversized/binary data, return explicit unavailable metadata.
  • If this package cannot be completed safely, retain preview-only behavior and report the blocker instead of faking a diff.
Gate: write-new and write-existing patches match actual before/after content; failure never appears applied.

08 — required checks

Verification commands and proof boundaries

Pi desktop lifecycle

Run/extend bun run --cwd apps/zyra-ui test:pi-assistant-lifecycle.

Desktop activity/diff contract

Run the focused activity rail contract and a dedicated file-change/diff contract if added.

TUI rendering

Run node scripts/test-zyra-ui-render.mjs after terminal renderer changes.

Targeted TypeScript

Use a temporary focused config covering only changed desktop contracts/runtime/service/renderer files.

Manual desktop smoke

Required for mounted panel selection and live refresh; compilation cannot prove clicks.

Manual TUI smoke

Required for real provider timing, scrollback behavior, expansion, and failure display.

Do not run: a production build, Rust build, deploy, packaging, destructive Git command, or broad unrelated test suite unless the user explicitly authorizes it or the implementation scope materially changes.

Proof language for the final handoff

  • A passing contract test proves the tested event/merge shape.
  • A targeted type check proves compilation for its included files.
  • A manual click-through proves mounted desktop behavior.
  • A real TUI smoke proves rendering under provider timing.
  • Anything not run must be named as unproven.
09 — agent operating rules

How the implementation agent should execute and report

Before editing

  1. Read the project AGENTS.md files and the companion implementation plan.
  2. Inspect every named target file; do not rely only on this spec’s line numbers because the working tree may have changed.
  3. Trace provider source → adapter → activity merger/store → component → rendered output.
  4. Inspect Git status without discarding unrelated changes.
  5. State the first scoped package and its focused verification before editing.

During implementation

  • Work package by package; do not combine lifecycle, panel wiring, TUI redesign, and write wrapping into one unreviewable change.
  • Keep provider extraction, normalized merge policy, and rendering in separate helpers/modules by responsibility.
  • Do not modify DevScope or Codex source. They are read-only references.
  • Do not overwrite current sidebar/timeline refinements unrelated to file changes.
  • Keep legacy/fallback payload behavior explicit and tested.

Stop and ask for input if

  • Safe write-existing snapshots require changing Pi SDK package source directly rather than a Zyra-owned wrapper/seam.
  • Current runtime event shapes differ materially from the researched fixtures.
  • Final turn-diff matching cannot be made unambiguous without a contract/schema change.
  • A production build, Rust build, destructive Git action, or broad architecture change becomes necessary.
  • Existing unrelated local changes overlap the same code blocks and cannot be preserved safely.

Required final report

  • Files changed, grouped by contract, provider adapters, merger, desktop, TUI, and tests.
  • What is wired end to end for Pi and Codex.
  • What remains fallback, provisional, mocked, assumed, or deliberately deferred.
  • Focused checks run and their results.
  • Manual behavior proven and anything still unproven.
  • A concise suggested commit message.
