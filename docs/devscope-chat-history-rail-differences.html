Official DevScope vs Zyra chat history rail investigation

This report is only about the central chat history/message rail: user/assistant messages, tool calls, agent/subagent activity, plans, issues, attachments, and the scroll/history display path.

Zyra UI: apps/zyra-ui DevScope: ../devscope Official report Code inspection only; no live visual smoke test was run.

Short summary

Renderer mostly matches DevScope

The core history renderer is mostly identical: AssistantConversationTimelinePane, AssistantTimeline, timeline entry/windowing, text rendering, attachment cards, issue cards, proposed plans, and subagent card components match DevScope.

Visible UI diffs are small but important

The actual central history display differs mainly in AssistantConversationPane, AssistantTimelineRows, and AssistantTimelineToolCallCard.

Agent/tool display likely diverges upstream

DevScope emits rich Codex events for subagents, file changes, diffs, MCP progress, approvals, and user-input. Zyra's Pi runtime emits much more generic message/tool events.

Main finding: if “agents and all that stuff” are not showing like DevScope, the component code is probably not the main issue. The bigger difference is that Zyra's runtime adapter is not producing the same specialized activity shapes that DevScope's Codex event mapper produces.

Runtime/event differences that affect what appears in the history rail

DevScope emits rich activity shapes

DevScope's codex-runtime-events.ts maps many Codex app-server events into specific activity kinds that the history rail can render specially:

  • thread/started with source: 'subagent', parent thread, agent nickname, role, depth, and cwd.
  • Collab agent tool calls mapped to subagent.spawn, subagent.send-input, subagent.resume, subagent.wait, and subagent.close.
  • turn/diff/updated mapped to a file-change activity with diff data.
  • rawResponseItem/completed, item/started, and item/completed mapped into command/file-change/search/MCP/dynamic-tool activities.
  • item/mcpToolCall/progress becomes MCP progress activity.
  • fuzzyFileSearch/sessionUpdated and completed become search activity.
  • approval.requested, approval.resolved, user-input.requested, and user-input.resolved are fully handled.
  • Reasoning, plan, assistant text, command output, and file-change output deltas have separate stream kinds.

Zyra Pi runtime emits fewer/simpler shapes

Zyra's ZyraPiRuntime currently maps:

  • message_update / message_end → assistant text delta/completed.
  • tool_execution_start / update / end → generic kind: 'tool' activity with summary like “Using/Used/Failed <toolName>”.
  • auto_retry_start → retry activity.
  • compaction_start → context compaction activity.
  • It emits thread.started, but without DevScope's subagent source/parent/nickname/role/depth metadata.
  • respondApproval and respondUserInput are no-ops in the runtime bridge.
History itemDevScope event shapeZyra UI event shapeDisplay consequence
Subagent activity subagent.* kinds or category: 'subagent'. Generic kind: 'tool' unless the Pi bridge manually sends subagent-looking data. The special “Subagent Activity” group/card probably will not appear.
Subagent thread metadata Thread started payload includes subagent parent/depth/nickname/role. Thread started payload is only provider thread id, cwd, state. Agent identity/thread hierarchy is not represented the DevScope way.
File changes/diffs Special file-change activities with patch/diff data. Generic tool result unless Pi emits a compatible result that the adapter maps later. Edited-file cards and diff affordances may be missing or generic.
Search/MCP/progress Specific search and MCP activity kinds. Generic tool activities. Less specialized display.
Approvals/user-input Requested/resolved lifecycle events. Runtime bridge methods are no-op; no equivalent event mapping was found in ZyraPiRuntime. Pending approval/input cards will not behave like DevScope unless another layer supplies events.
Empty assistant completions Can complete a message path even with no existing assistant text. service-runtime-events.ts returns early when there is no existing message and no assistant text. This avoids phantom blank assistant messages.

Most likely cause of the bad history rail

  1. The data is not DevScope-shaped anymore. Zyra's runtime adapter produces generic tool activities instead of DevScope's specialized subagent/file/search/MCP/activity kinds.
  2. Subagent display code exists but is likely not triggered. The renderer checks for subagent.* or category: 'subagent'; ZyraPiRuntime.emitToolActivity() emits kind: 'tool' with data.toolName.
  3. The empty-state behavior is intentionally different. Zyra hides the timeline entirely on empty chats and centers the composer.
  4. The plan-panel affordance is cut off. Proposed plan rows still render, but Zyra passes no onShowPlanPanel.
  5. Some history cleanup changed. Zyra recalculates thread message counts from actual messages, prunes orphaned thread rows, and skips empty assistant completions. These are probably improvements, but they can make old/invalid history look different.

Best next fix direction

Do not start by rewriting the visible timeline components. Start by adding a compatibility adapter in ZyraPiRuntime or the Pi bridge so agent/tool events are emitted in the same shapes DevScope expects:

  • Map tool names like agent spawn/send/wait/resume/close into subagent.* activities.
  • Emit subagent thread metadata when available: parent thread, nickname, role, depth.
  • Map file edits/diffs into file-change activities with patch/diff data.
  • Map search/MCP/progress events into their specialized DevScope activity kinds.
  • Only after data is compatible, tune the visual components if the layout still feels wrong.
