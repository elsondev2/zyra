Zyra capability platform

How Zyra can gain Codex-style browser control, desktop computer use, plugins and connected apps, visual inputs, interactive artifacts, and coding workflows without surrendering its Pi-based identity.

Decision: capability host
Best first proof: contained browser

Recommendation
Turn Zyra into a capability host, with Pi and Codex as interchangeable reasoning runtimes.

The target is broader than a coding-agent workbench. Zyra should host structured plugins and MCP apps, a contained browser, optional desktop computer control, visual and file inputs, generated artifacts, and the existing code/project workflow. Codex app-server provides the fastest OpenAI-native route for plugins, apps, MCP, OAuth, elicitations, dynamic tools, web search, and image inputs. Zyra must own the browser shell, permission ledger, cross-provider tool contract, artifact viewer, and any computer-control fallback.

First move

Build a contained, disposable browser session for localhost and public-page verification using Electron WebContentsView plus Playwright/CDP. It proves capability invocation, live screenshots, site approvals, action history, and agent steering without granting control of the user’s desktop or signed-in browser.

What the source audit established

02

Zyra has a solid conversation and coding-agent spine, but almost none of the broader desktop capability host exists yet. The Codex adapter already recognizes MCP tool activity; it does not yet expose marketplace, app, browser, computer, or artifact workflows to the renderer.

Working now

  • Desktop sessions, streaming, attachments, voice, tools, plans, queue and force
  • Pi multi-provider TUI, memory, web search/fetch, managed bash, skills and profiles
  • Codex app-server threads, approvals, plans, diffs and basic MCP activity projection
  • File preview, Monaco, Mermaid, xterm and node-pty foundations

Available to adapt

  • App-server plugin marketplace, install/read/uninstall, app/list and app mentions
  • MCP OAuth, status, resources, tool calls, forms and approval elicitations
  • Image/local-image turn inputs, web-search events and dynamic client tools
  • Plan, diff, details and terminal desktop inspectors

Zyra must add

  • Contained browser shell, profile isolation, CDP/Playwright control and annotation context
  • Desktop capture/accessibility host with per-app and sensitive-action policy
  • Plugin directory, connection manager, artifact viewer and interactive component sandbox
  • Permission ledger, action replay, redaction, emergency stop, worktrees and automation runner

Proposed product fit

03

The desktop remains conversation-first, but the right work surface can become a browser, app connection, generated artifact, code diff, terminal, or computer-control monitor. The TUI invokes and supervises these capabilities; rich visual output opens in the desktop surface or an exported local page.

Codex endpoint leverage map

05

These app-server methods are the shortest route to the broader capability layer. “Experimental” and “under development” methods must be discovered from the installed binary’s generated schema rather than assumed.

Discover and install

marketplace/add marketplace/remove marketplace/upgrade plugin/list plugin/installed plugin/read plugin/skill/read plugin/install plugin/uninstall app/list skills/list hooks/list

Connect and authenticate

account/login/start mcpServer/oauth/login mcpServerStatus/list config/mcpServer/reload mcpServer/resource/read mcpServer/tool/call plus OAuth completion and startup-status notifications.

Invoke capabilities

turn/start with text, image, local-image, skill, app and plugin mention inputs; streamed webSearch, mcpToolCall, and imageView items; command/exec and process/spawn for controlled utilities.

Host Zyra-owned tools

Experimental dynamicTools on thread start and bidirectional item/tool/call let Codex invoke Zyra’s contained browser, artifact renderer, screenshot capture, worktree service, or provider-neutral integrations.

Approve and elicit

Command, file, network and MCP approval requests; mcpServer/elicitation/request with URL, form and confirmation modes; tool/requestUserInput; permission-profile requests and exact available decisions.

Policy and environments

permissionProfile/list configRequirements/read including Computer Use policy, experimentalFeature/list, environment/add, environment/info, runtime workspace roots and selected capability roots.

Realtime and remote

Experimental thread/realtime/* for text/audio sessions and remoteControl/* for pairing, status and client revocation. These are later-phase surfaces because they add account and remote-execution risk.

Schema discipline

Run codex app-server generate-ts or generate-json-schema against the detected binary. Register only methods present in that schema, preserve maturity metadata, and fail closed on unknown payloads.

Recommended boundary

06

Reasoning runtimes do not directly control UI or external systems. They request named capabilities through one policy-enforcing host. The host owns credentials, sessions, approvals, screenshots, action history, and cleanup.

Reasoning and provider adapters

  • Pi / Zyra SDK bridge
  • Codex app-server JSON-RPC
  • Image and model providers
  • Future local or cloud agents
→

Zyra capability host

  • Registry: tools, plugins, apps, skills and surfaces
  • Policy: scopes, domains, apps, files and sensitive actions
  • Execution: browser, computer, MCP, terminal and dynamic tools
  • Evidence: screenshots, traces, outputs, citations and action log
  • Lifecycle: install, connect, revoke, abort and cleanup

Proof-led roadmap

Phase 0 · foundation

Capability host

  • Define capability descriptors, risk levels, scopes and output types
  • Persist approvals, revocations and action/evidence records
  • Add emergency stop and fail-closed runtime behavior
  • Generate app-server schemas from the detected Codex binary
Phase 1 · medium

Contained browser

  • Embed isolated WebContentsView sessions
  • Use Playwright/CDP for DOM, accessibility, screenshots, console, network and traces
  • Add site allow/block policy and sensitive-action approvals
  • Support element/area comments and verification evidence
Phase 2 · medium

Plugins and endpoints

  • Expose Codex marketplace, plugin and app discovery
  • Implement install detail, OAuth, MCP status/resources/tools and elicitations
  • Add @plugin, $app and skill mention UX
  • Bridge Zyra tools through version-gated dynamic client tools
Phase 3 · medium–high

Visual work

  • Expand image and screenshot attachments
  • Add image generation provider capability and edit lineage
  • Extend file preview to office/PDF artifacts and anchored annotations
  • Add sandboxed charts, maps, diagrams and interactive explainers
Phase 4 · red risk

Computer use pilot

  • Evaluate Codex Computer Use plugin and Qwen open-computer-use MCP
  • Approve one app and one task scope at a time
  • Show live screenshots, accessibility state, action budget and stop control
  • Block credentials, admin/security dialogs, payments and cross-app drift by default
Phase 5 · parallel work

Code and worktrees

  • Reconnect plan, diff, details and terminal surfaces
  • Add review and thread operations with Pi fallbacks
  • Build provider-neutral Git worktree lifecycle
  • Let browser/computer verification attach evidence to code turns
Phase 6 · high

Workflow composition

  • Run durable automations outside the renderer
  • Compose plugins, browser, computer, local tools and verification through skills
  • Add findings inbox, notifications and remote supervision
  • Pilot record-and-replay only after redaction and replay approval are proven
