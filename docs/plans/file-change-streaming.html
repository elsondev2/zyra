01 — decision and first move

Normalize the lifecycle before changing the cards

Decision
Build one provider-neutral file-change lifecycle, then adapt Codex and Pi into it.

The final activity ID is created at start, live revisions enrich that activity, and authoritative completion replaces provisional data without replacing identity, paths, timing, or output.

Fix first

Write lifecycle fixtures and merge-contract tests. They establish stable identity, patch authority, and out-of-order behavior before provider adapters or UI wiring can drift apart.

01

Immediate

Create the running row from the start event, even before complete patch arguments exist.

02

One identity

Every live and final update mutates the same provider operation.

03

Authoritative finish

Provider result or reconciled final turn data supersedes previews.

Improvement over DevScope: keep its stable started/completed lifecycle, add Codex’s current structured item/fileChange/patchUpdated protocol, and promote Pi result details into the real file-change model.

03 — researched findings

The renderer is capable; event normalization is the bottleneck

1

Stable lifecycle already exists

Zyra desktop Pi and Codex paths create a running activity and reuse its ID.

2

Pi details are dropped

Authoritative edit patch/diff fields survive transport but are not promoted for rendering.

3

Codex protocol moved

Structured patchUpdated replaced the emitted textual file-change delta.

4

Diff panel is disconnected

The live page explicitly passes an undefined diff callback.

Provider-shape-blind extraction

Pi details, Codex structured changes, argument previews, and final turn patches are handled as unrelated strings. Generic lookup cannot represent authority.

Obsolete live Codex path

Zyra still handles item/fileChange/outputDelta, whose type now states the server no longer emits it.

Custom TUI lost Pi semantics

Pi’s native component computes a call preview, then replaces it with result details. Zyra only keeps the generic output path.

Mounted-state break

AssistantDiffPanel and per-file actions exist, but AssistantPage passes onViewDiff={undefined}.

Normalized contract

Add a typed desktop contract under shared assistant contracts and a parallel JSDoc shape for the root TUI. Keep existing patch, paths, and stat fields as migration fallbacks.

type FileChangeSource =
  | 'args-preview' | 'provider-live' | 'provider-result'
  | 'turn-final' | 'synthetic-snapshot'

type NormalizedFileChange = {
  path: string
  previousPath?: string
  kind: 'add' | 'delete' | 'update' | 'move'
  diff?: string
  isNew?: boolean
}

type NormalizedFileChangePayload = {
  category: 'file-change'
  provider: 'codex' | 'pi'
  status: 'running' | 'completed' | 'failed'
  itemId?: string
  toolCallId?: string
  revision: number
  source: FileChangeSource
  authoritative: boolean
  changes: NormalizedFileChange[]
  paths: string[]
  createdPaths: string[]
  patch?: string
  previewPatch?: string
  additions?: number
  deletions?: number
  startedAt: string
  completedAt?: string
  durationMs?: number
  output?: string
}

Identity and authority

SourceAuthorityMerge behavior
args-previewLowestFill blank path/content immediately; never overwrite live or completed provider data.
provider-liveMediumReplace the previous snapshot for represented files; do not concatenate complete snapshots.
synthetic-snapshotMedium/highAuthoritative only when pre/post content is tied to the exact successful tool call.
provider-resultHighReplace preview/live patch for represented files while retaining lifecycle metadata.
turn-finalFinal reconciliationFill missing files or incomplete patch without replacing the real item activity.
Monotonic status

Completed or failed activity cannot regress to running after a delayed event.

Monotonic authority

Provisional content cannot replace provider-result or accepted final content.

Stable metadata

Preserve activity ID, created/start timestamps, paths, output, and errors.

Idempotent replay

Applying the same revision twice produces the same projected activity.

Snapshot semantics

Codex structured live changes replace the current same-file snapshot.

Safe ambiguity

If a turn diff cannot be matched confidently, keep it separate instead of corrupting an item.

Stable IDs: keep codex-item-${itemId} and zyra-tool-${toolCallId}. Never use a file path as the primary identity.
05 — desktop workstream

Normalize provider data, then wire the panel

A. Pi runtime extraction

  • Check, in order: result.details.patch, result.details.diff, partial-result details, explicit argument patch/diff, then synthesizable edit arguments.
  • Use Pi details.patch as the canonical desktop patch; retain details.diff as display-oriented data.
  • Read paths from result details/structured changes as well as top-level result and arguments.
  • At start, emit a provisional previewPatch once old/new edit arguments validate. At completion, promote the authoritative result on the same activity.
  • Keep raw result compatibility, but render from bounded normalized fields.

B. Current Codex runtime

  • Handle item/fileChange/patchUpdated before generic delta handling.
  • Normalize each {path, kind, diff} change, including update moves via movePath.
  • Emit to codex-item-${itemId} with source: provider-live.
  • Retain legacy item/fileChange/outputDelta as a documented compatibility fixture, not the primary architecture.

C. Lifecycle-aware service merger

  • Move file-change rules into a named helper with authority and revision tests.
  • Merge per-file changes by normalized current path and previous path for moves.
  • Recompute paths, created paths, file count, additions, and deletions after each accepted revision.
  • For final turn diff, prefer path overlap and latest incomplete activity in the same turn. Keep an unmatched final diff separate.

D. Mounted diff surface

  • Add selectedDiffTarget and minimal diff-panel state to the mounted AssistantPage.
  • Pass a real onViewDiff callback into AssistantConversationPane and mount AssistantDiffPanel.
  • Use DevScope’s proven state flow without copying unrelated playground, settings, plan, or details panels.
  • Key open selection by activity ID and file path so live revisions refresh the panel without remount flicker.
  • Show a restrained “Live preview” label until authoritative completion arrives.
Reuse, do not replace: AssistantDiffPanel, PatchDiffViewer, patch scanning, and per-file extraction already provide the required display machinery.
06 — TUI workstream

Restore authoritative result rendering in one mutable card

A. File-change-specific state

  • Keep Zyra’s existing one-component-per-tool-call lifecycle in src/zyra-ui.mjs.
  • Normalize path, preview patch, result diff/patch, source, revision, status, timing, and error before renderToolBlock.
  • Keep the forced tool-start invalidation; the row must not wait for completion.

B. Pi renderer semantics in Zyra’s component system

  • Build the argument-derived preview when required fields become complete.
  • At result time, prefer result.details.diff for terminal context and retain details.patch for stats/parity fixtures.
  • Show path, operation, +/− stats, and bounded context by default; use expansion instead of flooding scrollback.
  • Mutate the same component on completion. Never append a second final-diff card.

C. Partial arguments and failure

  • Render a running row even when path or replacement text is incomplete.
  • Regenerate and replace previews as streamed arguments become valid; do not concatenate them.
  • On failure, retain useful preview context but mark it uncommitted/failed.
Boundary choice: do not directly embed Pi’s native TUI component. Reproduce its call/result data semantics inside Zyra’s own host, theme, spacing, and transcript behavior.
07 — write-tool decision

Exact write-existing diffs require execution-boundary enrichment

Pi edit already returns authoritative patch details. Pi write returns the target path and new content in arguments but no successful result details.

Recommended

Wrap or enrich the write tool

Capture a bounded pre-write snapshot inside the tool execution boundary, execute the built-in behavior, then return compatible content plus normalized diff/patch details. This guarantees correlation to the exact tool call and avoids bridge-delivery races.

Safe interim

Show a provisional content preview

Synthesize a correct add-file preview for new files. For existing files, show new content as provisional and do not claim it is a before/after diff.

Snapshot guardrails

  • Cap bytes and lines; detect binary/null bytes; retain hashes when content is omitted.
  • Keep snapshots in memory per tool call and delete them on completion, failure, cancellation, or session disposal.
  • Preserve encoding and newline style where possible; label normalization where exact preservation is unavailable.
  • Never persist full pre-edit snapshots as separate logs or telemetry.
  • For oversized/binary files, retain path/status/size and a specific “diff unavailable” reason.

Acceptance criteria

  • File-change row appears on the first start event in desktop and TUI.
  • Known paths appear before completion; incomplete arguments cannot crash rendering.
  • One provider operation retains one stable activity/component ID.
  • Pi edit completion uses result.details.diff/patch.
  • Current Codex patchUpdated updates the running activity in place.
  • Final turn diff preserves item identity, timing, paths, and output.
  • Desktop Diff action opens the mounted panel on the correct file.
  • An open live diff refreshes without panel remount flicker.
  • TUI completion replaces provisional content in the same card.
  • Write-new has a correct add patch.
  • Write-existing is snapshot-backed or explicitly preview-only.
  • Failed operations never present a preview as applied.
  • Legacy persisted patch/path payloads continue to render.
  • Full snapshots and secrets stay out of logs and telemetry.
Project constraint: use focused contract tests and targeted type checks. Do not run a production build unless explicitly requested or the implementation becomes massive.
09 — what could break it

Risks and guardrails

High risk

Late events regress completed state

Guard with revision plus monotonic status and authority rules.

High risk

Turn diff attaches to the wrong edit

Require turn and path overlap; keep ambiguous final diffs separate.

Medium risk

Large patches freeze a surface

Cap lines/bytes, lazy-parse desktop data, and bound TUI context.

High risk

Write snapshot races execution

Capture inside a wrapped tool boundary, not asynchronously in UI event delivery.

Medium risk

Provider patch formats diverge

Use canonical unified patch for desktop while retaining structured/display data.

Medium risk

Persisted sessions grow sharply

Persist bounded normalized fields; retain raw payload only for required compatibility.

Non-goals

  • Replacing AssistantDiffPanel, PatchDiffViewer, or Zyra’s terminal component host.
  • Making desktop and TUI visually identical.
  • Copying unrelated DevScope settings, playground, plan, or details-panel architecture.
  • Removing legacy persisted activity support in the same change.
  • Changing DevScope or Codex source, or requiring Rust builds.
