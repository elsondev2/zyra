- Signing, notarizing, publishing a release, creating a public tag, or exposing an updater release.
- Installing software, modifying PATH, replacing credentials, changing accounts, or clearing Browser/user data.
- Force-pushing, rebasing published commits, or otherwise rewriting history.
- Destructive cleanup of ambiguous user files.
- Paid/provider-backed Chat or Voice calls unless separately approved in the parent session.
- Accepting a remote Voice endpoint/model override at runtime.

Never commit secrets, private local memory, raw private exports, user profiles, credentials, caches, generated dependency trees, disposable screenshots, or local test documents. If any appear, leave them untouched and ignored locally; do not delete ambiguous files.

## Execution method

For every checklist item:

1. Reproduce or establish the actual current state.
2. Trace the source of truth end to end.
3. Identify the root cause.
4. Add or strengthen a deterministic regression test when feasible.
5. Make the smallest maintainable fix.
6. Run the narrowest canonical validation lane from `docs/development/fast-validation.md`.
7. Re-run the reproduction.
8. Update `docs/plans/v0.6.0-weekend-readiness-checklist.md` with status and evidence.
9. Commit only after the batch is internally coherent and its focused checks pass.

If a first fix fails, stop stacking patches. Reproduce again and instrument the uncertain assumption.
